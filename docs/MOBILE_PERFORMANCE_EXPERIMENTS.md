# Mobile startup experiments — 26 November 2026

This branch starts from stable `main` commit `42a9c90`. It contains a focused performance experiment, not a redesign. The production website has not received these changes. Lighthouse JSON and Chrome traces are kept in ignored local `.lighthouseci/` files; no private data is included in this document.

## Baseline and method

The earlier production mobile Lighthouse runs scored 84, 77 and 77 (median 77). A representative 77 run reported 1,052 ms Total Blocking Time (TBT), about 1,695 ms style/layout work and 897 ms JavaScript evaluation. LCP was 1.4 s and CLS was 0 in that run. The production measurement and its limits are described in `docs/POST_RELEASE_PERFORMANCE.md`.

For controlled comparisons here, each experiment used the same laptop, Chrome, Next.js production build, 390×844 mobile viewport and `scripts/lighthouse.mjs --mobile` settings. Three runs were made for each state; the medians are more useful than a single score. The laptop, browser cache, CPU contention and Lighthouse simulation still introduce noise. `scripts/profile-mobile.mjs` also recorded a separate 4× CPU-throttled Chrome trace and precise JavaScript function coverage against a local production server. Trace event durations are diagnostic samples, not equivalent to Lighthouse TBT.

The first experiment produced the strongest early improvement. The contact split's additional one score point and eight milliseconds of median TBT are within normal run-to-run variation. It is retained mainly because static contact information can remain a server component, while only the interactive form needs hydration. Later runs on the same laptop became highly variable: both layout and script evaluation increased together on slow runs, including runs without the anchor rule. Consequently, this branch has **not** demonstrated a reliable score above 90 or a median TBT below 200 ms. The early results show potential, while the later results limit confidence. The anchor rule remains because removing it caused a confirmed deep-link regression.

## What the traces and bundles show

The baseline 4× CPU trace recorded about 2,275 ms of `Layout`, 368 ms of `UpdateLayoutTree`, and 1,109 ms of `EvaluateScript`. With below-fold visibility the corresponding single trace recorded about 1,501 ms, 291 ms and 1,118 ms. The final split version's single trace recorded about 1,679 ms, 335 ms and 1,077 ms. These event totals may include nested or different-thread work, so they should not be added as a page total. Their direction supports a reduction in initial layout work; JavaScript evaluation stayed near 1.1 seconds in these traces.

The baseline DOM contained roughly 559 elements. Precise Chrome coverage showed many functions in shared chunks were not called during initial page load, including the React DOM chunk, but those functions may be needed for later interaction or other routes. The largest shared React DOM chunk contains `hydrateRoot` and is about 228 KB raw / 71 KB gzip. The Next.js client chunk is about 165 KB raw / 45 KB gzip. The contact-related chunk shrank from about 27.2 KB raw / 10.3 KB gzip to 25.9 KB raw / 9.6 KB gzip after the server/client split. Removing the form's static links from the client boundary therefore saved only about 0.7 KB gzip; the common React runtime still loads for the header and form.

## Individual decisions

1. **Below-the-fold rendering:** `app/globals.css` applies `content-visibility: auto` to skills, experience, qualifications, projects, services and contact sections. The browser can defer internal layout until a section nears view. A direct hash link initially stopped short because the skipped sections used estimated heights; `main:has(.section:target)` now turns the optimization off for anchor navigation. A Playwright regression checks a direct `/#contact` visit and keyboard focus. The safeguard's independent cost could not be isolated reliably under the laptop's variable load; three runs with it removed were also slow.
2. **Deferred contact hydration:** not implemented. A lazy placeholder would make a visible form temporarily unusable, and the existing JSON API does not accept a plain no-JavaScript form submission. A safe progressive-enhancement conversion would be a separate feature change. The measured score already exceeded 90 without it.
3. **Client component boundaries:** `components/ContactSection.tsx` now renders static details on the server; `components/ContactForm.tsx` remains a client component for validation, submission and feedback. `components/HeaderClient.tsx` stays interactive for navigation. `components/ProjectCatalogue.tsx` is route-specific and does not load on the homepage.
4. **Bundles and dependencies:** no obvious unused production dependency was found: the fonts, icons, Next.js/React, Resend and Zod serve current routes. The shared React runtime is the largest browser cost; removing a necessary dependency or disabling JavaScript would harm functionality. Chrome function coverage is a starting point for route-level analysis, not proof that uncovered code is removable.
5. **Hydration:** the production trace's long React DOM task and the persistent ~1.1 s script-evaluation sample show that CSS does not eliminate hydration work. The form and header still need it. Server rendering keeps portfolio content visible and indexable before hydration.
6. **Layout and CSS:** the large Layout event is the clearest bottleneck. The new CSS reduced layout time in the paired traces and the early lab series, while CLS stayed at zero. Later TBT measurements were inconsistent, so a sustained user benefit remains to be verified on a quieter machine or real devices. The anchor safeguard is essential because estimated section heights otherwise make deep links unreliable.
7. **Images and fonts:** Lighthouse marked font display, responsive image sizing and offscreen image loading as passing. It estimated about 32 KiB of possible hero portrait image savings and about 156 ms from render-blocking CSS in one baseline run. The portrait is already small and visually important; further compression or delaying the essential stylesheet was not justified by this experiment.

## Verification and limits

Formatting, ESLint, TypeScript and the production build passed. The production dependency audit found zero vulnerabilities. Playwright passed 28/28, including a new direct `#contact` link and keyboard-focus check. Desktop Lighthouse scored 99/100/100/100. Mobile accessibility, best practices and SEO scored 100 in the recorded runs; mobile performance varied from 76 to 93 in the final six runs. The direct link, mobile navigation, all ten case studies and contact form behavior remained passing. A production measurement can only be made after a separately approved merge and deployment. If field data later shows slow interaction despite a lab score, profile the actual device path rather than chasing another Lighthouse point.
