# How this portfolio reaches the screen

This guide explains the browser and security work behind the portfolio. Use it with the source files and Chrome DevTools. The exercises use local builds and dummy data; they require no AI assistant or real credentials.

## From HTML to pixels

1. The browser parses the HTML response into a **Document Object Model (DOM)**: a tree of elements. Next.js sends the homepage markup from the server, so the main content exists before browser JavaScript runs. `app/page.tsx` renders `components/Portfolio.tsx`, which assembles the hero, experience, projects and contact sections.
2. The browser parses `app/globals.css` and `tokens.css` into a **CSS Object Model (CSSOM)**. It combines CSS rules with DOM elements during **style calculation**. A selector or inherited style may affect many descendants.
3. **Layout** calculates each visible box's size and position. Changing text width, grid tracks or an element's dimensions can force layout again. The portfolio has a long homepage with many cards, so its initial style and layout work matters on a slow phone CPU.
4. **Paint** draws text, borders, shadows and images into layers. **Compositing** arranges those layers on screen. Some transforms and opacity changes can be composited without laying out the entire page, but promoting too many layers also consumes memory.

The production mobile Lighthouse baseline on 26 November 2026 was 84, 77 and 77 (median **77**). In a representative 77 run, Lighthouse attributed about **1,695 ms to style/layout**, **897 ms to JavaScript evaluation**, and **188 ms to script parsing/compilation**. Largest Contentful Paint was **1.4 s** and Cumulative Layout Shift was **0**. These are measurements under Lighthouse's simulated mobile conditions, not every visitor's experience. See `docs/POST_RELEASE_PERFORMANCE.md` for the original review. Experiment results are recorded in `docs/MOBILE_PERFORMANCE_EXPERIMENTS.md`.

## JavaScript, the event loop and React

The browser's main thread handles JavaScript, style, layout and much interaction work. The **event loop** takes a task, runs it to completion, then can process the next task. A task longer than 50 ms is a **long task**. During a long task, a tap or key press may wait. Lighthouse's **Total Blocking Time (TBT)** adds the portions of long tasks beyond 50 ms between First Contentful Paint and Time to Interactive. The baseline TBT was about **1,052 ms**. Two measured tasks were about **675 ms** (document attributed) and **451 ms** (in the React DOM client chunk). Minified production bundles prevent assigning all that time to one application function.

`components/Portfolio.tsx` is a **server component**: it can produce HTML without shipping its own component code to the browser. `components/HeaderClient.tsx` and `components/ContactForm.tsx` use `"use client"` because navigation state, form submission and feedback need browser events. `components/ProjectCatalogue.tsx` is another client component on the project catalogue route. A client boundary makes its imports part of a browser bundle. Keeping static sections on the server reduces code sent to visitors, but a small client component still needs shared React and Next.js runtime code.

**Hydration** is React connecting client components to server-rendered HTML so clicks, input and state updates work. The baseline trace showed a large shared React DOM task containing `hydrateRoot`. Server-rendered markup alone can look complete while interaction is still waiting for hydration. **Code splitting** breaks browser code into chunks that load where needed; **lazy loading** can defer a chunk until later. Either approach must preserve accessible controls, stable markup and prompt first interaction. The contact form must still validate and deliver messages, and the menu must work immediately when opened.

Images and fonts also affect rendering. Project screenshots use optimized WebP where appropriate, and `next/image` controls responsive loading in the case-study components. The homepage's leading visual and font should load promptly; below-the-fold images should not compete with them. Inspect the Network panel rather than assuming a small file is harmless: decode and layout costs also count.

## Lighthouse and user experience

Lighthouse runs a lab test with a controlled device and network model. Its performance score combines several timings; it is useful for comparing controlled experiments but varies between runs. Use the median of at least three runs on the same build, machine and settings. `scripts/lighthouse.mjs` starts a production build, launches an isolated Chrome profile and writes JSON to `.lighthouseci/mobile-report.json`. The production baseline's mobile accessibility, best practices and SEO scores were all 100. The desktop baseline was 100 in all four categories.

**Core Web Vitals** are field metrics: Largest Contentful Paint (LCP) for loading, Interaction to Next Paint (INP) for responsiveness and Cumulative Layout Shift (CLS) for visual stability. TBT is a lab proxy for potential interaction delay; it is not INP. A score improvement is useful only if navigation, form use, keyboard access and real visual quality remain sound. Never remove real content or weaken tests just to alter a lab score.

## Why deleting a secret is insufficient

Git commits point to content objects. Removing a file in a new commit changes the latest tree, but older commits and clones can still contain the object. Compressed archives are another blind spot: a scanner that checks only visible file names may miss `.env` or token files inside a ZIP. Detailed repository security findings and owner actions belong in private records outside this public repository.

**Credential rotation** means issuing a new secret in its owning service, updating legitimate consumers and invalidating the old one. For an obsolete account, revoke or lock it after confirming it is unused. Moving a repository to private or rewriting Git history does not revoke a leaked credential or erase copies already downloaded. Store new secrets in protected environment configuration or a secret manager, keep templates such as `.env.example` free of real values, and use local or CI secret scanning before publishing. Never submit confidential files to an external scanner without authorization.

Select a Layout event and note its duration; do not assume all events are caused by JavaScript.        |

Then visit `/projects`.                                                    | The catalogue route loads code that the homepage does not need. Coverage percentages describe bytes used during that capture, not proof that unused bytes can all be deleted. |
| Observe hydration          | In DevTools Network, throttle to Slow 4G and CPU to 4× slowdown; reload and try the menu and contact form. Repeat with JavaScript disabled.                                                                     | Server text still appears with JavaScript disabled, while client interactions do not work. Re-enable JavaScript and verify they work; note when controls become responsive.   |
| Repeat a lab measurement   | Run `npm run build`, then `npm run lighthouse:mobile` three times. Record performance, TBT, LCP and CLS from each `.lighthouseci/mobile-report.json` before the next run overwrites it.                         | Scores vary. Use the median and compare the same metric under the same conditions; a single high score is weak evidence.                                                      |

Never use a real credential for this exercise.                                                |

After each exercise, write down what you observed, the exact command or DevTools panel used, and one reason the result might differ on another device. That note is enough to repeat the investigation independently.
